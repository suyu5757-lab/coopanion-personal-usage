# C2-08 Handoff 文件与 SQLite 恢复 — owner: `core/persona.ts` and `core/memory/hindsight.ts`

Date: 2026-11-03
Status: **Local crash-window recovery implemented and exercised; C2-08 remains PARTIAL for untested power-loss and filesystem-specific behavior.**

## Recovery record and order

The protocol reuses the existing SQLite v4 `derived_artifact` row for `handoff-note`. Its `lifecycle_state` records `pending`, `active`, `stale` or `withdrawn`; existing `creatorOperationId` stores an owner token containing the artifact ID, staging device/inode and staging filename. The artifact stores the note digest, scope, dependencies and lineage receipt. No table or migration was added.

1. `prepareHandoff()` recovers previously registered handoffs, writes a mode-0600 staged file, fsyncs it and its staging directory, and retains the staged inode identity.
2. `commitHandoffArtifact()` writes a SQLite `pending` provenance row before publication.
3. The Persona publishes the same inode by hard link and fsyncs the Handoff directory.
4. SQLite activates the artifact only while owner, digest, source epoch and source dependencies still match.
5. The staged link is removed after activation; the containing directory is synced.

SQLite COMMIT and filesystem link publication are separate operations. The implementation does not describe them as one atomic transaction.

Recovery runs when Persona prepares another Handoff or a protected `handoffs/` file read is attempted. All `handoffs/` file reads remain withheld. Recovery processes only SQLite-registered Handoff artifacts and a staged/final file whose owner token, device/inode and body digest match. It verifies current source read-backs before activating a pending artifact. Unknown/unregistered stage files remain in place and withheld; stale final notes are preserved as history while their owned stage link can be removed.

## Tested crash windows

| Window | Test | Result |
|---|---|---|
| Staging exists before a SQLite owner row | `withholds an unregistered Handoff stage after restart and keeps its unconfirmed owner` | Stage remains; workspace read is refused. Recovery does not claim an owner that never committed. |
| Pending SQLite owner committed before publish | `publishes a staged Handoff after restart when its pending SQLite owner matches` | Restart links the matching staged inode, validates the source and activates the note. |
| File published; SQLite activation commit fails | `recovers a published Handoff after activation commit fails and the SQLite owner matches` | Pending row and published file are reconciled after reopen; note activates only after dependency recheck. |
| Forget wins after publish and before activation | `keeps a published Handoff stale when Forget wins before SQLite activation` | Activation fails; lifecycle stays stale, final history is preserved, owned stage is removed, file remains unreadable. |
| SQLite activation succeeds; stage cleanup is interrupted | `removes an owned staging link after restart when SQLite activation already committed` | Reopen removes only the stage inode recorded by the owner token. |
| Candidate is discarded or changes epoch before commit | `blocks a staged protected handoff when the forget epoch changes before commit`; `publishes once and discard removes only the candidate file it owns` | No stale artifact enters the new context; discard is limited to the matching staged/final inode. |

The existing negative commit case `keeps a handoff published before failed SQLite commit out of later workspace reads` remains in the same test file; an unregistered published file is refused and is not automatically deleted.

## Remaining recovery boundary

Tests simulate process stops by cutting execution at protocol boundaries and reopen temporary SQLite. They do not simulate machine power loss, kernel/filesystem cache loss, media corruption or every directory-fsync failure. Recovery is lazy on the next protected read or Handoff preparation; it is not claimed as an eager startup sweep. C2-08 remains `PARTIAL` until those platform behaviors are addressed by the owning contract and independently verified.

All fixture files and databases are test-owned under system temporary directories and are removed by test cleanup. No user note, private workspace, production SQLite or installed App was accessed.
