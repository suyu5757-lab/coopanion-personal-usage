# C2-09 Forget 状态机与持久恢复 — owner: `core/memory/forget-ledger.ts` and `core/memory/state-store.ts`

Date: 2026-11-03
Status: **Implemented and locally verified; C2-09 remains PARTIAL/GATED at the first-write durability boundary.**

## Implemented sequence

`MemoryStateStore` reuses the existing SQLite v4 `memory_deletions`, `memory_fences`, `memory_derived_state` and `memory_metadata` rows. No table, migration, file, second Bank or external coordinator was added.

| State | Durable evidence | Runtime behavior | Result visible to caller |
|---|---|---|---|
| `REQUESTED` | No row yet | The current call has an in-process block while resolving targets | No acceptance claim |
| `DURABLE_INTENT` | `memory_deletions.state='intent'` and `forget:write-blocked=1` commit in one SQLite transaction | All Memory reads, activation and delivery fail closed until promotion | `accepted`, with pending deletion work |
| `FENCED_PENDING_REMOTE` | Source fence, namespace epoch, derived invalidation and retry task are committed; the temporary global block is cleared | The exact bank/endpoint/document tuple stays fenced; remote deletion can retry | `accepted`; `pending` or `failed` reports remote work state |
| `REMOTE_ACK` | Delete is verified and the deletion task is durably marked `done` | The fence remains; a later read cannot restore the old source | `accepted`, `deleted` counts verified acknowledgements |
| `FAILED_NOT_ACCEPTED` | Intent write failed and read-back found no intent | Current process stays blocked; an exact retry can be attempted if its fallback marker was stored | `not-accepted`; caller must retry |
| `UNKNOWN_BLOCKED` | Storage state or acceptance cannot be established, or a persistent block has no recoverable intent | Memory remains unavailable | `unknown-blocked`; no completion claim |

`ForgetLedger.beginIntents()` is the acceptance boundary. It writes intents before queue cancellation or fences. `HindsightMemory.forgetDocument()` and natural-language `forget()` then cancel matching Outbox rows and promote intents inside a SQLite transaction. The transaction updates fences, epochs, derived lifecycle rows and retry tasks together. If promotion fails, the already committed intent remains blocked and the call returns `accepted` with pending work. Loading a ledger promotes persisted intents before Memory reads can proceed.

External deletion failures leave retryable tasks. A successful delete is counted only after the existing delete verification path finishes. `memory_forget` reports the acceptance state and counts, and says that current conversation text may remain.

## Fault results

All cases use temporary SQLite v4 and synthetic source IDs.

| Injection | Exact test | Observed result |
|---|---|---|
| Intent write and fallback marker both fail | `tests/memory-state-store.test.ts` — `reports an unaccepted Forget when the initial intent and fallback block cannot persist` | The call returns `not-accepted`; the current instance blocks reads. After reopening, the fixture contains no intent, fence or marker and the source is visible again. This is the demonstrated limit; the request cannot be reconstructed from failed storage. |
| Intent commits; fence insert fails | `recovers a durable Forget intent after the fence transaction fails` | The call returns `accepted`, one task remains pending, and current reads are blocked. After dropping the injected trigger and reopening, the intent becomes a fence plus pending task; the source remains invisible. |
| Derived invalidation fails during fence promotion | `rolls back fence and epoch when derived invalidation fails, then recovers the intent` | SQLite rollback leaves intent plus global block, with no partial fence or epoch. Restart promotes after the fault is removed and marks the derived artifact stale. |
| Remote delete fails, then process reopens | `retries a failed remote deletion after reopening SQLite` | First result is accepted with retryable failure; fence survives. Reopened task retries and is verified done; source remains fenced. |
| Process exits after intent commit, before promotion | `recovers a durable intent after the process exits before fence promotion` | Child process exits after the intent commit. Reopening promotes the intent before the ledger reports healthy; the fence and task are present. |
| Late retain callback during pending intent | `blocks a late retain callback while a durable intent awaits fence recovery` | Callback cannot activate the source while recovery is blocked. |
| Same document ID in another namespace | `keeps bank clear fences inside one namespace when document IDs overlap` | Wildcard clear fences only its bank and endpoint; the other namespace stays usable. |
| Remote bank clear fails and is retried | `keeps the wildcard fence after remote bank clear fails and retries only on a later clear call` | Wildcard fence survives reopen and remote error. A later explicit clear completes and removes only the target namespace's wildcard fence. |

`tests/memory-state-store.test.ts` — `keeps stored activation inaccessible when the source fence transaction fails` additionally checks that a global write block hides activation while the raw activation and mention rows remain intact. This distinguishes a safety block from destructive partial cleanup.

## Remaining boundary

If the intent transaction and fallback block write both fail, this process can reject the request and block reads until exit, but after restart SQLite has no record to identify the failed request. The source may be visible again. No implementation can recover a request that left no durable trace; no cross-restart promise is made. C2-09 therefore remains `PARTIAL/GATED` pending any contract or independent storage design. The implementation has not added a second medium.

Bank clear is a separate wildcard-fence flow. Its retry is explicit on a later clear call; this batch did not add automatic remote clear retries at startup.
