# Patch C2-B SQLite v4 migration — owner: core/memory/state-store.ts

## 判定

`C2_B_PARTIAL/GATED`。SQLite v4 与来源依赖存储已实现，空库、v2、v3 升级和故障回滚有合成测试。v1 没有可核实的历史 DDL 或可重放数据库，因此版本 1 目前 fail closed，不能宣称 v1→v4 已验收。

## v3 现有职责

`MemoryStateStore` 的 v3 schema 含以下持久表：

| 表 | 持久职责 |
|---|---|
| `memory_metadata` | legacy import 标记与 Forget 损坏状态 |
| `memory_events`、`memory_operations` | outbox 事件及投递状态 |
| `memory_revisions` | Bank/endpoint 内的修订关系 |
| `memory_deletions`、`memory_fences`、`memory_derived_state` | Forget 删除任务、source fence、scope epoch/stale 标记 |
| `memory_activation`、`memory_mention_events` | v3 activation 锚点与已验证 user mention |

升级前对 version、表名、列名和具名索引作精确检查。`memory_derived_state` 的 `(bank_id, endpoint)` epoch/stale 语义保持原样，v4 未将它改作 artifact 表。

## v4 结构

| 表 | 主键 | 内容 |
|---|---|---|
| `generation_evidence` | `(session_id, generation_id)` | provider attempt、response/tool correlation、origin、mapping state、receipt digest、验证时间与异常原因；`actual_evidence_used` 受数据库约束固定为 `unknown` |
| `generation_source_dependency` | generation 复合键 + `(bank_id, endpoint, document_id)` | 完整来源 namespace、Forget epoch/fence、revision、content/segment digest、验证状态和 correlation |
| `derived_artifact` | `artifact_id` | kind、target、scope、creator generation/operation、body digest、origin、review/lifecycle/lineage state 与状态原因 |
| `derived_artifact_source` | artifact + `(bank_id, endpoint, document_id)` | 派生物到来源的完整 tuple、epoch/fence、revision、digest、验证状态和 correlation |

来源唯一索引覆盖完整 Bank、endpoint、document tuple。`document_id` 相同但 Bank 或 endpoint 不同的来源不会碰撞。记录只保留 body digest 和来源元数据，不保存 provider request/response body 或长期 Memory 正文。

`complete` 和 `source-independent` 都要求 receipt digest 与验证时间。`source-independent` 必须显式指定并且来源集合为空；空集合默认仍是 `unknown`。有不完整 lineage 的 artifact 不能以 `active` 写入。状态 API 可以将 artifact 标为 `pending`、`stale`、`withdrawn`、`withheld` 或 `unknown`；没有将其自动恢复为 `active` 的操作。

## 类型化存储 API

- `saveGenerationEvidence` / `getGenerationEvidence` 写入并读取 generation 及多父来源。
- `saveDerivedArtifact` / `getDerivedArtifact` 写入并读取 artifact 与来源关系。
- `derivedArtifactsForSource(bankId, endpoint, documentId)` 以完整 namespace 查找。
- `markDerivedArtifactState` 写入显式状态与原因，不改变 lineage。

相同身份和完全相同的内容幂等；同一 generation/artifact identity 出现 revision、digest 或其他元数据冲突时抛错，不静默覆盖。来源输入中的完全相同 tuple 会去重，数据库复合主键再次保证唯一性。只有 LLM/tool 调用方能提供的元数据会写入；本批未接入 C2-C consumers。

## 迁移事务

- 空库必须没有用户表、view 或 trigger。空库初始化和后续 v2/v3 DDL 都在同一个 `BEGIN IMMEDIATE` 事务中完成。
- 已确认的 v2 schema 从 v2 补 v3 activation/mention 表，再增加 v4；v3 直接增加 v4。旧表与 durable rows 不重建。
- `PRAGMA user_version=4` 在所有 DDL、索引、schema 检查、`quick_check` 和 `foreign_key_check` 成功后写入，并与 DDL 一起提交。
- 故障注入在 v4 DDL 完成、版本号写入前抛错。重开后仍为 v3，旧行逐表相同，v4 表不存在；重试后升级成功。
- v4 重复启动不改 schema。未知/额外/缺失的旧表、列、索引、非预期新版本及 user_version 1 均 fail closed。
- v1 不提供迁移猜测。历史仓库记录指出已核对的 storage 源码为 v2，且未找到真实 v1 DDL；旧版低版本兼容分支并不构成 v1 schema 合同。可复核资料：`scratch/r1-r2-offline-preparation-report-20261029.md`、`scratch/i1-stateful-migration-precheck-20261029.md`，以及本地 ref `codex/memory-v2.3` 的 `core/memory/state-store.ts`。

## PARTNER v1 sidecar 边界

`core/memory/partner-provenance.ts` 继续管理独立的 PARTNER provenance JSON：工作区 digest、段落 digest、origin、来源 IDs、source-scope digest 和 current/stale 状态。PARTNER.md 正文仍在工作区文件，sidecar 不保存段落正文。SQLite v4 不复制或迁移该文件，也不改变现有读取、编辑、source fence 和失效逻辑；`tests/partner-provenance.test.ts` 在本轮通过 8 项。

## 验证范围与未接线内容

v4 migration 与存储 API 使用短命合成 SQLite。测试未打开生产 SQLite、Hindsight Bank、私人 Workspace、PARTNER 文本、正式 App、账号或模型。`retainCoo`、`pet_say`/`pet_ask`、Growth/Experience/PARTNER consumers、Forget/revision 传播、自动解除 stale 状态仍属于 C2-C，未在本批接线。没有正式产品验收，状态为 `NOT_RUN_FORMAL_APP`。

完整 B01–B12 和 R2 回归证据见 `scratch/v2.0-c2-b-test-matrix.md`；Git 与保护文件核对见 `scratch/v2.0-c2-b-git-closeout.md`。
